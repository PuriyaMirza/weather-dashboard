## Findings, ranked by how often the underlying pattern recurred across sources

### 1. Users want raw numbers translated into a word/judgment, not just a figure — and this project already does this
**Mixed: WebSearch snippets (unverified) + directly read GitHub issue.**
- What people want: not "UV index 7" but "that's high, cover up"; not "dew point 64°F" but "that's muggy." This came up as the implicit ask behind several sources: coaching content explicitly maps dew point ranges to pace-adjustment advice for runners (55–65°F "adjust 1–3%," 65–70s "adjust 5%+"); the OSHA/NIOSH Heat Safety Tool app converts temperature + humidity into five named risk tiers (minimal/low/moderate/high/extreme) specifically so outdoor workers don't have to interpret a raw heat-index number themselves.
- Reason given: raw numbers require domain knowledge (is 64°F dew point bad? most people don't know) that a word-label removes.
- Frequency/sources: recurring across three unrelated domains — running-coach blogs (`marathonintelligence.substack.com`, `triplethreatlife.substack.com`), the government OSHA/NIOSH heat-safety tool and its landscaping-trade-press coverage, and (as a design decision rather than a complaint) Breezy Weather's own module design.
- Links: https://marathonintelligence.substack.com/p/dew-point-and-performance , https://triplethreatlife.substack.com/p/how-to-adjust-run-pace-in-the-heat , https://www.dol.gov/general/apps/heatindex , https://www.landscapemanagement.net/niosh-osha-update-heat-safety-app-for-outdoor-workers/

**Bucket: fits current architecture — already substantially built.** I read `lib/weather/metrics.ts` directly (not a web source — the project's own code) and this pattern is already implemented for UV (Low/Moderate/High/Very high/Extreme), dew point (Muggy/Noticeably humid/Dry and comfortable), humidity, cloud cover, visibility, pressure trend, and AQI category — every one of these pairs a number with a spoken-word qualifier, matching exactly what the sourced complaints above say they want from other apps. **This is a validation finding, not a to-do.** The one gap: there is no heat-index-style word label built from `feelsLikeF` the way the OSHA tool does (e.g., "Caution" / "Extreme caution" / "Danger" bands). That would be a small, buildable addition — same shape as `describeUv`, no new data needed, since Open-Meteo's apparent temperature already feeds `feelsLikeF`. Flagging as a plausible next single-reading module, not asserting it as heavily demanded (the sourcing here is a government tool's existence and trade-press coverage, not direct user complaint quotes).

### 2. Composite/cluttered panels vs. wanting to isolate and reorder individual metrics
**WebSearch snippet, unverified by me** (from a search-engine summary of Apple Community discussion `discussions.apple.com/thread/250350809`, which I could not open directly — blocked).
- What people want, about Weather Underground's app specifically: the current-conditions block "takes up way too much room" forcing scrolling before reaching the daily forecast; users don't all want the radar shown before the daily forecast; a direct quote-adjacent paraphrase describes the interface as "cluttered with boxes... unnecessary boxes for tonight, tomorrow, tomorrow night"; the 10-day graph got moved off the front page behind extra clicks and slow loads.
- Reason given: the app's designers chose one fixed composite layout; users wanted to choose their own arrangement and omit sections they don't use.
- Frequency/sources: one search-engine-summarized thread, so treat as a single data point, but it echoes the same shape as finding 3 below (Breezy Weather) and the general premise of this project.
- Link (unverified — I could not open it myself): https://discussions.apple.com/thread/250350809

**Bucket: fits current architecture — already built.** This is close to a direct restatement of what card customization, module-level granularity (12 single readings vs. 9 composite panels), and drag/keyboard reordering already solve here. No action needed; useful as external validation that "let me rearrange and omit boxes" is a real complaint pattern about a named competitor, not a solution in search of a problem.

### 3. Wanting to choose which chart/metric appears in a given widget, rather than a fixed bundle
**Directly read** — GitHub, Breezy Weather (open-source Android weather app) issue #937 ("Widgets overhaul").
- What people want: per-widget selection among Temperature, Air quality, Wind, UV index, Precipitation, Feels like, Humidity/dew point, Pressure, Cloud cover, Visibility (hourly) and a shorter list for daily — explicitly citing an earlier issue (#676) asking for "other hourly data (precipitation, air quality, etc) in hourly widget" because the fixed default widget didn't match what a given user tracks.
- Reason given: different users prioritize different data (air quality vs. precipitation vs. temperature trend) and a one-size widget can't serve all of them.
- Frequency/sources: one project, but it's a maintained open-source app solving the identical design problem this project already solved differently (modules vs. widgets) — useful as a cross-check, not a vote count.
- Link: https://github.com/breezy-weather/breezy-weather/issues/937

**Bucket: fits current architecture — already built**, same as finding 1/2. The single-reading module list in `lib/weather/metrics.ts` (12 metrics, independently addable/removable/reorderable) is the same shape of solution Breezy Weather is still building toward. Nothing to change; flagging because it's a clean, direct-read confirmation that this design direction is sound, from a comparable app's own issue tracker rather than a marketing page.

### 4. Wind direction "from" vs. "to" ambiguity
**Directly read** (developer.apple.com WeatherKit forum thread) + **WebSearch snippet** (YBW sailing forum, unverified).
- What people want: consistent, unambiguous labeling of which way a wind-direction arrow/compass points. The WeatherKit thread shows a developer genuinely confused about whether "90°, East" meant "wind FROM the east" or "wind blowing TO the east" — resolved as: WeatherKit is correct (direction wind comes from) but under-documented at the point of display, and the confusion was compounded by an actual iOS 15 regression where directions were briefly shown backwards. A sailing-forum thread (unverified) independently describes the same "from vs. to" convention mismatch across weather products generally, describing it as something apps seem to "choose randomly," and notes some apps now let users toggle the convention.
- Reason given: meteorological convention (direction wind comes FROM) is not the intuitive reading of a compass arrow for a lay user, and apps disagree on which they use.
- Frequency/sources: two sources, one directly read (developer forum) and one unverified snippet (sailing forum), plus an Apple internal version-to-version inconsistency as a concrete example of the failure mode.
- Links: https://developer.apple.com/forums/thread/709279 (directly read) ; https://forums.ybw.com/threads/forecast-wind-arrow-frustation.627703/ (unverified snippet)

**Bucket: fits current architecture — already built correctly.** I checked `metrics.ts`: the wind module already renders `"From the {compass}"` in words, not just an arrow glyph or bare degrees — which sidesteps this exact ambiguity by construction (Project constraint: "No information conveyed by colour alone" already pushed this toward words generally). No action needed; flagging as confirmation the project's existing wording choice avoids a real, sourced confusion pattern in competitor apps.

### 5. Historical/past-weather comparison ("what was it like yesterday/last week")
**Directly read** (developer.apple.com thread, one user's feature request — explicitly told by a forum moderator it was the wrong venue) + **WebSearch snippet** (existence of a small cluster of dedicated apps: "Yester — Yesterday's Weather," "Weather with Yesterday," "Cool or hot today?", "Yestoday: Artful Weather").
- What people want: a graph or short summary of the past 24 hours to 7 days of actual conditions at a location, shown symmetrically with the forward-looking forecast, so a user can recall or compare "was today unusually warm."
- Reason given: forward forecasts already get 7–10 days of visual treatment; nothing in mainstream apps mirrors that backward.
- Frequency/sources: one directly-read single-user request (low weight on its own) plus a small product category (indirect market evidence, same caveat as run 1's activity-window apps finding — a market existing is not the same as a sourced complaint thread).
- Links: https://developer.apple.com/forums/thread/759091 (directly read) ; app existence only, unverified: https://apps.apple.com/app/id6466406778 (Yester), https://apps.apple.com/app/id6450978243 (Weather with Yesterday)

**Bucket: out of scope — confirmed against an explicit non-goal.** PRD §3 non-goals table already lists "Historical weather or climate data — Out of scope for a 'today' dashboard." This finding doesn't change that; it just supplies sourced evidence that the desire is real, so the non-goal is a deliberate trade-off rather than an unconsidered gap. Not recommending reversal.

### 6. Forecast uncertainty not communicated (10-day/daily numbers shown as if certain)
**WebSearch snippet, unverified by me** (search-engine summary of Apple Weather commentary, source page `leancrew.com` blocked to me directly; also referenced by `cultofmac.com` per the same search).
- What people want: some acknowledgment that a 10-day snow forecast is a probabilistic guess that "will almost always fluctuate wildly" rather than a flat number presented with the same visual confidence as tomorrow's forecast. A related, distinct complaint in the same search: users confused when the hourly view shows a 30–40% precipitation chance for "today" but the daily detail view shows 0.0 for today with rain not expected for three days — an internal consistency problem between two views of the same underlying data, not an uncertainty-communication problem per se.
- Reason given: no visual or textual distinction between a high-confidence near-term number and a low-confidence far-out number.
- Frequency/sources: one search-engine-summarized article plus one adjacent (and different) complaint about hourly/daily inconsistency, both unverified by me directly.
- Link (unverified): https://www.cultofmac.com/news/how-weather-apps-mislead-users

**Bucket: would need a constraint check, not a change per se.** True uncertainty bands (ensemble spread) are a different Open-Meteo product line (its ensemble API) from the deterministic forecast this project currently calls — whether the free non-commercial tier covers it, and whether the normalizer/schema work is small or large, is unresearched and should be a follow-up technical question, not assumed either way. The narrower, cheaper fix — visually or textually de-emphasizing far-out daily numbers relative to near-term ones — needs no new data, but I found no sourced request specifically asking for *that* narrower version; the sourced complaint is about the "flat 10-day number" problem broadly. Flagging as a genuine open question rather than a bucketed recommendation.

## Buckets, summarized

**Fits current architecture (already built or trivially extendable):**
- Number + word-label pairing for UV, dew point, humidity, cloud cover, visibility, pressure trend, AQI — already shipped (`lib/weather/metrics.ts`), validated against sourced external complaints (finding 1).
- A heat-index-style word band built from existing `feelsLikeF` (Caution/Extreme caution/Danger, OSHA-tool-style) — not shipped, but same shape as `describeUv`, no new data source needed (finding 1, weak-to-moderate sourcing).
- Per-metric card isolation and reordering instead of fixed composite panels — already shipped, validated against a competitor complaint (finding 2) and a comparable open-source app's own roadmap (finding 3).
- "From the {compass}" wind-direction wording — already shipped, sidesteps a sourced real ambiguity (finding 4).

**Would need a constraint change, or is an open technical question rather than a bucketed yes/no:**
- Visual/textual uncertainty treatment for far-out daily forecasts (finding 6) — depends on whether Open-Meteo's ensemble data is reachable under this project's free/non-commercial constraint; unresearched, flagged for a follow-up technical spike, not a product recommendation either way.

**Out of scope:**
- Historical/past-weather comparison (finding 5) — directly conflicts with the existing "Historical weather or climate data" non-goal in PRD §3. Sourced demand is real but thin (one misdirected feature request plus a small app category); not a reason to reverse the non-goal.
